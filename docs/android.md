# Maharani Traders — Android app

Documentation for the native Android wrapper around the existing
**Maharani Traders** web application.

> **This app contains no business logic.** It is a thin native shell
> (Capacitor) whose WebView loads the already-deployed production site.
> Every price, GST calculation, cart rule, order, credit ledger, approval
> flow, RLS policy and role check runs on the server exactly as it does in
> a mobile browser. Nothing is duplicated, cached or faked inside the APK.

## 2. Production URL

```
https://maharani-mart-mahakali108s-projects.vercel.app
```

Defined once, in `capacitor.config.ts` (`PRODUCTION_URL`), overridable with
the `CAP_SERVER_URL` environment variable when running `npx cap sync`.
`www/offline.html` has a single `RETRY_URL` constant that must be kept in
sync manually (documented in that file).

Scheme is `https` (`androidScheme: 'https'`), `cleartext` (plain HTTP) is
**disabled**, and `allowMixedContent` is **false**.

> Vercel **Deployment Protection** must be OFF for the Production
> environment, otherwise the WebView is redirected to a Vercel SSO login
> instead of the app. Vercel dashboard → Project → Settings → Deployment
> Protection → “Only Preview Deployments” or “Disabled”.

## 3. Architecture

```
Android APK (Capacitor WebView, https scheme)
      │  server.url  (no app code bundled)
      ▼
Vercel — Next.js 14 (Server Components, Server Actions, middleware.ts)
      │  cookie session via @supabase/ssr, service-role key server-side only
      ▼
Supabase (Postgres + Auth + RLS)
```

- `webDir` is `www/` and only ever serves `offline.html`
  (`server.errorPath`), shown when the remote URL cannot be reached.
- The web assets under `www/` are **not** the app: they exist only for the
  offline screen and so the Capacitor CLI has a `webDir`.
- Static export (`output: 'export'`) is not viable for this codebase — see
  `AUDIT_ANDROID.md` for the full reasoning (Server Actions, middleware,
  cookie sessions, per-request Supabase queries).

## 5. Build process

### 5.1 Continuous integration (GitHub Actions)

Workflow: **Android Debug APK** (`.github/workflows/android-apk.yml`)

#### Which version is active?

There are two copies of this workflow:

| File | State |
| --- | --- |
| `.github/workflows/android-apk.yml` | **active today.** Node 20 + `npm install`, `actions/checkout@v4` / `setup-node@v4` / `setup-java@v4`, Debug APK only. |
| `docs/android-workflow-apk-aab.yml` | **finalized target**, not yet active. Node 22 LTS + pnpm, `actions/checkout@v5` / `setup-node@v5` / `setup-java@v5`, web quality gates, explicit Android resource validation, explicit Android SDK component install, `aapt` identity verification, and a conditional Release AAB stage. |

`docs/android-workflow-apk-aab.yml` could not be activated directly by the
automation because the GitHub App token used to maintain this repository
does **not** have the `workflows` permission:

```
! [remote rejected] … (refusing to allow a GitHub App to create or update
  workflow `.github/workflows/android-apk.yml` without `workflows` permission)
```

A human with normal write access activates it with:

```bash
cp docs/android-workflow-apk-aab.yml .github/workflows/android-apk.yml
git add .github/workflows/android-apk.yml
git commit -m "CI: promote finalized Android APK/AAB workflow"
git push
```

Both versions produce the same artifact name
(`maharani-traders-debug-apk`) and the same package ID, app name and
version, so promoting is safe and non-breaking.

#### Currently active workflow

Triggers:

- `workflow_dispatch` — *Actions → Android Debug APK → Run workflow*

Steps:

1. Checkout (`actions/checkout@v4`)
2. Node 20 (`actions/setup-node@v4`)
3. JDK 17 Temurin (`actions/setup-java@v4`) + Android SDK
4. `npm install`
5. `npx cap add android`
6. `npx cap sync android`
7. `./gradlew assembleDebug`
8. Upload the `maharani-traders-debug-apk` artifact

#### Finalized workflow (`docs/android-workflow-apk-aab.yml`)

Triggers:

- `workflow_dispatch` — *Actions → Android Debug APK → Run workflow*
- `pull_request` — when Capacitor/resources/scripts/www files change
- `push` to `main` — when those same files change

Steps, in order:

1. Checkout (`actions/checkout@v5`)
2. Node.js 22 LTS (`actions/setup-node@v5`)
3. pnpm via corepack (version from `package.json#packageManager`)
4. `pnpm install --frozen-lockfile`
5. Web quality gates: `pnpm typecheck`, `pnpm lint`, `pnpm test`
6. `pnpm build` (Next.js production build)
7. `npx cap add android` (fresh native project)
8. `npx cap sync android` (runs the post-sync hook)
9. `node scripts/android-resource-validation.mjs` — Android resource names
10. JDK 17 Temurin (`actions/setup-java@v5`) + Android SDK
11. `sdkmanager "platforms;android-34" "build-tools;34.0.0"`
12. `./gradlew assembleDebug` (debug-signed by Gradle’s own keystore)
13. Locate the APK and assert it exists and is non-empty
14. Verify **package ID**, **application label** and **version** with `aapt`/`aapt2 dump badging`
15. Upload the APK artifact
16. Build + upload a Release AAB **only** if the signing secrets exist

### 5.2 Local build

```bash
pnpm install --frozen-lockfile
npx cap add android          # first time only; android/ is gitignored
npx cap sync android         # copies brand resources + stamps version
                             # (runs scripts/android-postsync.mjs automatically)
cd android && ./gradlew assembleDebug
# → android/app/build/outputs/apk/debug/app-debug.apk
```

Release bundle (requires the owner’s real upload keystore — see §6). The
signing wiring is deliberately **not** generated by `npx cap sync`, so a
Debug build is always produced from exactly the project Capacitor
generated. Create it locally when you need a signed release:

```bash
cat > android/signing.gradle <<'GRADLE'
android {
    signingConfigs {
        release {
            storeFile file(System.getenv('ANDROID_KEYSTORE_FILE'))
            storePassword System.getenv('ANDROID_KEYSTORE_PASSWORD')
            keyAlias System.getenv('ANDROID_KEY_ALIAS')
            keyPassword System.getenv('ANDROID_KEY_PASSWORD')
            enableV1Signing true
            enableV2Signing true
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
        }
    }
}
GRADLE
grep -q 'signing.gradle' android/app/build.gradle \
  || printf '\napply from: "../signing.gradle"\n' >> android/app/build.gradle

export ANDROID_KEYSTORE_FILE=/absolute/path/upload.keystore
export ANDROID_KEYSTORE_PASSWORD=…
export ANDROID_KEY_ALIAS=…
export ANDROID_KEY_PASSWORD=…
cd android && ./gradlew bundleRelease
# → android/app/build/outputs/bundle/release/app-release.aab
```

`android/` is gitignored, so neither the wiring nor the keystore can be
committed.

Equivalent npm scripts: `pnpm android:build:debug`,
`pnpm android:build:release`.

## 6. Signing

### Debug APK — no configuration required

`assembleDebug` is signed by Gradle’s auto-generated debug keystore
(created in `~/.android` on the runner machine). It is not a secret, is
never committed, and is not valid for Play Store publication.

### Release AAB — owner credentials required

> **Release AAB signing requires the owner's upload keystore/secrets.**

The finalized workflow (`docs/android-workflow-apk-aab.yml`, once promoted)
never generates, guesses or fabricates a keystore, key, password or
service-account file. If the secrets below are absent, the AAB steps are
skipped with a visible `::notice::` annotation and in the job summary, and
the Debug APK is still built and uploaded. The currently active workflow
does not build an AAB at all.

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 upload.keystore` output for the Play upload keystore |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | upload key alias |
| `ANDROID_KEY_PASSWORD` | upload key password |

Add them under **Settings → Secrets and variables → Actions → New
repository secret**.

How they are used (finalized workflow):

- The workflow decodes `ANDROID_KEYSTORE_BASE64` to
  `$RUNNER_TEMP/maharanitraders-upload.keystore` at build time and exports
  its path as `ANDROID_KEYSTORE_FILE`.
- Still inside the AAB-only path, the workflow writes
  `android/signing.gradle` (gitignored along with the rest of `android/`)
  which wires `signingConfigs.release` from `ANDROID_KEYSTORE_FILE`,
  `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
  `ANDROID_KEY_PASSWORD`, with both v1 and v2 signing enabled (minSdk 22
  needs v1), and applies it from `android/app/build.gradle`.
- A Debug build therefore never sees any signing wiring at all: it is built
  from exactly the project `npx cap sync` produced.
- The keystore file is deleted from the runner in an `if: always()` step.

Play Store publication additionally needs a Google Play service-account
with *Release → View app information / Manage production releases*
permission; it is **not** used by this repository’s CI and must never be
committed.

## 8. Android resource directory validation

Android requires resource qualifiers in one canonical order (Table 2 of
<https://developer.android.com/guide/topics/resources/providing-resources#table2>):
orientation (`port`/`land`) → UI mode → night mode (`night`/`notnight`) →
density (`mdpi`…`xxxhdpi`).

So splash directories **must** be named:

```
drawable-port-night-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}
drawable-land-night-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}
```

and **must never** be named `drawable-night-port-*` or
`drawable-night-land-*` — those are rejected by the resource merger with
“Invalid resource directory name” and fail `:app:mergeDebugResources`.

`scripts/android-resource-validation.mjs` enforces this and is run:

- automatically by `scripts/android-postsync.mjs` on every `npx cap sync`
  (fails before anything is copied), and
- explicitly as its own CI step, because the Capacitor CLI does **not**
  fail `npx cap sync` when a task hook exits non-zero.

The validator only judges qualifier tokens it recognises; unknown tokens
(locales, `sw<N>dp`, `b+…`) cause that directory to be skipped, so it can
never reject a valid directory it does not understand.

Run it manually:

```bash
node scripts/android-resource-validation.mjs
```

## 9. Security

- No Supabase **service-role key** is present in the Android project, in
  `www/`, in `resources/` or in the CI workflow. The service-role key is
  used only by server-side Next.js code (`lib/supabase/server.ts`).
- No keystore, password, alias, service-account JSON or `.env` file is
  committed. `android/` is gitignored, and `.gitignore` also blocks
  `*.keystore`, `*.jks` and `local.properties`.
- `cleartext` traffic is disabled; `allowMixedContent` is false; the
  WebView uses the `https` scheme.
- CI runs with `permissions: contents: read`.
- The release-signing wiring reads credentials from environment variables
  only, and the decoded keystore is removed from the runner afterwards.

## 10. Supabase / auth / database

**Unchanged by the Android app.** Authentication is the existing
server-side, cookie-based Supabase session; middleware and RLS continue to
be authoritative. The Android wrapper adds no new auth path, no new role,
no new table, no new policy and no migration.

## 11. Known limitations

1. **Remote-URL app.** The APK ships no application code: it needs
   internet access and loads the live site. There is no offline catalog,
   cart or ordering — only the branded “No internet connection / Retry”
   screen (`www/offline.html`).
2. **No native push notifications** (Capacitor Push Notifications plugin is
   not installed; `google-services.json` is absent, so push is inert).
3. **Debug APK is not publishable** to the Play Store; a release build with
   the owner’s upload keystore is required.
4. **Release AAB path is unverified in CI** until the owner adds the four
   signing secrets — the steps are skipped until then, by design.
5. **`www/offline.html` `RETRY_URL`** is a manual sync point with
   `PRODUCTION_URL` in `capacitor.config.ts`.
6. **Vercel Deployment Protection** must stay disabled for Production, or
   the app opens a Vercel SSO login page instead of the storefront.
7. **Back button** walks the WebView history and only then hands control
   back to the system (which backgrounds the app — it does **not** log the
   user out) via the generated `MainActivity.java`.
8. `pnpm build` runs in CI as a quality gate even though the APK does not
   bundle its output.
