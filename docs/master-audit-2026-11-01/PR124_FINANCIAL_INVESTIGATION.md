# PR #124 — wallet financial blocker investigation

**Date:** 2026-11-05. **Status:** investigation and isolated design experiment only; owner approval and implementation are pending. PR #124 must remain **draft and unmerged**. No production wallet code, Supabase migration or production data was changed in this investigation. No repository migration was applied, including locally. No real wallet transaction was run.

## 1. Existing accounting convention — establish the sign first

`supabase/migrations/0029_retailer_wallet_ledger.sql` stores positive integer paise in `amount_paise`; `direction='debit'` increases what the retailer owes and `direction='credit'` decreases it. The authoritative `get_retailer_outstanding_paise` in `0031_wallet_outstanding_opening_baseline.sql` calculates:

```
outstanding = opening_outstanding_paise
            + sum(non-reversed money-movement debits)
            - sum(non-reversed money-movement credits)
available = credit_limit_paise - outstanding
```

`CREDIT_LIMIT_CHANGE` entries are excluded, because they are not money movements. Positive outstanding is money owed; negative outstanding means the account is in credit, not a negative debit. Available credit increases when outstanding decreases. A zero balance plus ₹500 order debit should give +₹500 outstanding; a linked ₹500 refund should bring it to ₹0. With only a ₹200 partial refund it should remain +₹300. Opening balances can be nonzero. The `retailers.outstanding_balance` field is a rupee-valued legacy mirror updated by a ledger trigger, not normally the baseline input after migration 0031. The no-account fallback has special behavior and needs separate review.

## 2. Root cause — a reversal is counted twice

`0031` excludes any original row once `is_reversed=true`, but `0053_order_coin_refund.sql` both inserts an active `ORDER_REVERSAL` credit and marks the original `ORDER_DEBIT` reversed. For a ₹500 debit with zero opening:

| State | Counted debit | Counted credit | Outstanding | Change from pre-refund |
|---|---:|---:|---:|---:|
| Before refund | ₹500 | ₹0 | +₹500 | — |
| After 0053 credit, before flag | ₹500 | ₹500 | ₹0 | −₹500 |
| After 0053 also flags debit | ₹0 | ₹500 | **−₹500** | **−₹1,000** |

Thus the debit's removal and the credit each reduce outstanding by ₹500, overstating available credit by ₹500 relative to the intended post-refund state. The corresponding mirror trigger runs on ledger insert/update, but a production incidence or its magnitude has not been measured. Existing `tests/wallet-ledger.test.ts` explicitly expects the defective −₹500 behavior; passing it is not correctness proof. The previously added `tests/coin-refund-balance-db.test.ts` asserts the correct ₹0 result and is unchanged (git blob `db01a4bcd4a5f327dc7e492bc8c8d1fb5f3a1739`). It previously failed against local PGlite/actual migration history; **it was not rerun now** because its harness applies repository migrations, which this task forbids.

## 3. Trace and boundaries

- **Debit:** `0031`'s `check_and_debit_retailer_wallet` locks the credit account, checks existing idempotency key before and after the lock, checks available credit and appends `ORDER_DEBIT`. `0082_category_tier_pricing.sql` can create separate debits per child, all referencing the parent order with child-scoped keys. Key replays in the existing debit RPC do not appear to validate that an existing row's payload matches the new request.
- **Parent refund:** `0053` authorizes the retailer, staff or a no-session internal case, requires cancelled/returned parent status, selects **only the earliest** order debit without locking it, inserts one positive credit with `reversal_of` and `reversal:<debit-id>`, then flags that debit. A function call is transactional for its own statements. A duplicate of this same key is limited by the global unique key and `ON CONFLICT DO NOTHING`, but a no-debit/already-reversed result or key conflict returns zero without validating the existing credit's amount, ownership or link. Unique-key protection for one key is not a general per-debit refundable-balance constraint.
- **Partial child refund:** `0067_seller_settlement.sql` locks each matching child debit and calculates `least(requested, debit amount)`, but uses one `reversal:<debit-id>` key and marks the **entire** debit reversed even for a partial credit. Consequently partial refunds cannot safely accumulate; 0031 additionally excludes the whole original debit, so a ₹500 debit plus ₹200 credit can produce −₹200 rather than +₹300. Parent and child paths may race or overlap; the parent RPC does not coordinate through the same debit lock.
- **Other adjustments:** `lib/admin/wallet-actions.ts` also inserts an opposite-direction reversal and marks the source reversed in separate requests; `lib/orders/wallet-reversal.ts` has a similar non-transactional legacy fallback for some non-cancellation callers. `0053`'s `order_shortfall_coins(..., p_reverse=true)` instead flags an existing credit without appending an opposite entry. Changing the balance function to count *every* flagged row without first migrating this flag-only convention would create a different error. `lib/delivery/delivery-actions.ts` invokes parent refund and shortfall reversal separately; some results are not checked.
- **Cancellation transaction:** retailer web (`lib/retailer/order-actions.ts`), mobile (`app/api/mobile/v1/orders/[id]/cancel/route.ts`) and admin (`lib/admin/orders-actions.ts`) first commit an order status change, then call `restoreAndVerifyCancellationCoins`, then release coupons. The verifier can reject multiple debits **after** status commit. It checks a full credit/flag pairing, not the resulting balance, so the double-counted single-debit state may pass. `lib/admin/sub-order-actions.ts` performs status, stock and child refund as separate calls and does not check all refund/stock results. Other seller/return paths and stock/coupon triggers require complete transactional inventory.
- **Constraints and concurrency:** `0029` requires positive amounts, restricts direction/type values, gives `idempotency_key` a nullable unique constraint and `reversal_of` a foreign key. Those constraints do not themselves enforce matching retailer/order, opposite direction, one refund event identity, cumulative refunded <= source debit, or valid transaction-type/direction pairs. Admin update policies and mutable flags mean the existing ledger is **not immutable in the strict sense**. The frozen opening baseline is outside the ledger. `0031`'s account lock protects its debit routine but not every direct writer, old refund or shortfall path. Idempotency alone does not serialize different partial keys or guarantee transaction-level all-or-nothing cancellation.

## 4. Proposed minimal direction — NOT implemented, owner decision required

The smallest conceptual correction is to apply **one** reversal effect, never both: retain the monetary debit in the balance and append the actual refund credit; treat a fully-refunded marker as metadata, not another monetary exclusion. For example, with current formula, a *new* debit kept unreversed plus a ₹200 credit gives ₹300. That observation is not a safe one-line patch: existing idempotency, shortfall reversal, admin reversals, all `is_reversed` consumers, historic rows and partial/refund writers rely on today’s mixed conventions.

Recommended design to evaluate, not production code:

1. Define a single append-only money-movement convention: positive amounts and explicit debit/credit, including offsetting entries for reversals. Make flags non-monetary metadata or derive status; credit-limit changes remain excluded. Retain or immutably record a provable opening baseline. Correct old flag-only conventions and both read paths only under a reviewed migration/reconciliation plan.
2. Require a source debit belonging to the correct retailer/order/child and a valid refundable event. Distinguish a valid zero-Coins order cancellation (no refund operation needed) from a request to credit a missing/invalid debit (reject). Bind the authenticated actor server-side; enforce least privilege and hardened search paths.
3. Serialize **all** competing operations on agreed account/order/debit locks in a globally consistent order, including checkout, cancellation, child refunds, return/shortfall, admin reversal and direct writes. Re-read state after locks. Within one transaction, sum prior linked refunds and reject requests exceeding the remaining original debit; account for earlier shortfall credits and subsequent reversals without double counting. Enumerate every split debit. Order/child status, stock, coupon and ledger must commit together where required; audit and authorization must be part of the same transaction.
4. Use a unique immutable refund-event/request key scoped to the business event (rather than one key per entire debit). Same key + same validated payload is idempotent; key reuse with a different payload is an error. A separate partial event may refund only remaining value. Add database constraints/privileges to prevent unlinked, mismatched, excessive or duplicate writes; guard against bypass by old writers. Multi-debit allocation and duplicate events across different source debits need a precise event/allocation model.
5. Make every balance reconcile from a verified opening plus all effective immutable money movements, independent of a mutable mirror. Prove separately whether and how legacy data can be brought into that model; do not assume historical flags correspond to valid linked credits. Add append-only enforcement appropriate to owner/admin/service role permissions, while recognizing database superusers can bypass ordinary triggers.

The synthetic fixture demonstrates one candidate for a fresh, single-debit system, not an implementation plan ready to ship. It does not implement real schema, actor/RLS controls, all writer paths, multi-debit allocation, production triggers, security-definer permissions, or production migration. The fixture's lock order is illustrative only, not a proven global application lock hierarchy.

## 5. Migration, historical repair and rollback considerations

A deployable fix would require at least a new ordered database migration and coordinated application changes; **none are provided or applied here**. A balance-only alteration or clearing existing `is_reversed` flags globally would mis-handle flag-only shortfall reversals, partial credits, conflicting keys, missing credits, duplicate links, old manual adjustments and migrated opening baselines. Historical balances may already have influenced subsequent orders/credit use; do not assume the double-count is a simple cash loss or automatically charge/debit customers. No production data has been queried, so affected accounts and amounts are unknown.

Before a future authorized change: back up and verify recovery; inventory and classify every historical reversal and shortfall, ambiguous/partial/duplicate rows, source identity, transaction chain and baseline; reconcile proposed vs current balances per account against independent records; require an accounting/owner-reviewed exception list; rehearse on a disposable production-like snapshot with privacy controls. Reconcile immutable audit events and mirror values explicitly. Never silently change or delete financial history. Any repair must be a separately approved, auditable, idempotent plan, not part of this investigation.

Rollback planning must distinguish **before any new writes** from **after new writes**. Before writes, a reviewed code/schema rollback may be possible after validating compatibility. After writes under a new convention, blindly restoring old balance logic can recreate double counting; stop affected writes/traffic under an approved incident plan, preserve journal and backups, reconcile, and use a tested forward correction or point-in-time recovery with full operational approval. This is a plan to develop, not an executed rollback.
