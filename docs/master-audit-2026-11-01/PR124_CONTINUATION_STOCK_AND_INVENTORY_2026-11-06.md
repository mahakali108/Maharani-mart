## Current path audit — release blockers

- Retailer website, admin/staff and mobile parent cancellations still update order status separately from refund verification. The 0088 atomic RPC is not wired to these paths; it rejects *all* split orders and does not implement staff permission parity. A network timeout after an RPC is ambiguous and must not be represented as definite rollback. Coupon handling must be made transactional and verified for owner/admin/staff.
- Seller `seller_update_sub_order` cancels and restores child stock in its own database transaction but does not refund child Coins. Admin child handling and delivery return/refund still span calls. Parent aggregation may invoke the parent stock trigger; 0089 fixes stock ownership, not financial or status atomicity. Map lock order, partial refunds, child ownership, shipment/stock counters, retries and all settlement/allocation interactions before wiring. Seller ledger/payments are a separate plane; no Coins credit is seller settlement.
- `lib/admin/wallet-actions.ts:reverseTransactionAction` is a separate direct ledger writer: it inserts a compensating entry and then flags the original in a second call. The outstanding RPC excludes flagged originals, so this can misstate balances; it can also race partial order refunds and does not enforce their cap. It has not been fixed by 0088/0089 and requires an atomic, authorized event design and migrated-schema concurrency tests. Other direct ledger grants/writers must be reviewed as well.
- Remaining truncated/duplicate readers include retailer ledger's first-1000 spending/credit totals, salesman dashboard spent calculation and some legacy account mirrors. Admin detail explicitly labels its recent aggregates, but they are not lifetime totals. Android uses mobile API data and must be audited end to end. The remaining changes and independent app/DB concurrency tests are mandatory.
- No Super Admin recovery/bootstrap was implemented or rehearsed. Do not create/promote an account automatically. Recovery needs independently reviewed identity verification, least-privilege manual authorization, single-use/expiry and audit, and realistic Auth integration testing. Current zero-user observations do not prove recoverability.

## Reset and restore decision gates — design only, no reset script

1. Freeze writers and external integrations in an approved maintenance window; inventory live tables, column-level semantics, complete FK graph (including outside public), policies, triggers, functions, scheduled jobs/webhooks, Auth providers/settings, Storage buckets/objects and external stores. Classify every table and object prefix, including audit and legally retained evidence, with an owner and professional retention decision. Snapshot versions and row/object counts without exporting secrets in logs.
2. Verify a complete DB backup including Auth records/hashes, migrations and audit history and store it securely. Independently export all Storage object bytes and metadata with checksums and retain required configuration/infrastructure manifests. Neither a DB-only backup nor the current zero-object query verifies this.
3. Restore into an explicitly authorized isolated destination without production credentials; verify schema/migrations, RLS, routines/triggers, Auth login/recovery, representative linked financial rows, inventory, membership/rewards and seller separation; compare counts and object checksums, verify Storage permissions, then document timing and rollback. This may require paid infrastructure and owner approval; no such restore has occurred.
4. Only after independent sign-off, prepare a deterministic reviewed, audited, idempotent execution/rollback plan using supported Auth/Storage APIs and FK-aware ordering, preserving schema/configuration and required evidence. No blanket cascade, manual auth-table deletion, retention cleanup or automatic Super Admin promotion. Explicitly authorize each live operation separately. This repository contains no executable reset plan and no live reset was requested or run.
