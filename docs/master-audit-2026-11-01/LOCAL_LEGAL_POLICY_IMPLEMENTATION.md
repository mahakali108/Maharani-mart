### Trace and exact local changes

- Retailer web: `components/retailer/order-actions-panel.tsx` invokes `lib/retailer/order-actions.ts`; the action commits an owned pending-order status change via Supabase, then separately performs a Coins reversal and coupon release. The old implementation ignored both returned reversal errors and thrown errors and reported success. The panel now offers a check/retry for an already-cancelled order, and the action allows a retry only after an owner-filtered status read.
- Mobile: `app/api/mobile/v1/orders/[id]/cancel/route.ts` had the same separate status update and reversal and logged errors while returning 200. It now returns 503 with a clear partial-state message when restoration cannot be verified and allows an owner-filtered retry; missing, foreign and non-cancellable orders retain a generic conflict.
- Admin: `lib/admin/orders-actions.ts` now uses the same verification, supports an already-cancelled retry and uses a status-matching update to avoid cancelling a concurrently changed order. The generic `updateOrderStatusAction` routes cancellation through the checked cancellation action and requires its cancellation permission as well; returned orders are not moved back to cancelled.
- New `lib/orders/cancellation-coins.ts` reads the caller-visible ledger with an exact row count, rejects incomplete/error reads and multiple order debits, calls the existing single-debit `refund_order_coins` RPC, and verifies a single matched credit, amount, direction and reversed flag before reporting success. It returns an explicit error if restoration or verification is uncertain. `lib/orders/wallet-reversal.ts` now supports `requireRefundRpc` for cancellation so a missing RPC cannot silently invoke the legacy, non-transactional direct-write fallback. Existing non-cancellation callers retain that fallback and were not otherwise changed. Coupon release remains a separate best-effort operation.
- Existing SQL source `0053_order_coin_refund.sql` uses an idempotency key `reversal:<debit id>` and performs credit insertion plus debit marking within that **refund RPC**, but the RPC first requires the order already be cancelled/returned and only examines the earliest debit. It does not atomically cancel the order. Modern split checkout in `0082_category_tier_pricing.sql` can create **one debit per child**. The local verifier deliberately refuses to claim success for multiple debits instead of invoking the single-debit RPC as though it refunded the full order. The refusal occurs **after** the existing status update, so such an order can remain cancelled with Coins not restored; support/reconciliation is required. This is a serious remaining blocker, not a complete refund fix.
- Other paths also need transactional design and review: seller `sellerUpdateSubOrderAction` can change child status and aggregate parent status; `adminTransitionSubOrderAction` invokes child status, stock restoration and `refund_sub_order_coins` in separate calls and currently does not inspect their errors; delivery-return handling also calls the old reversal helper separately. The child refund SQL can use a partial amount while marking the debit reversed, which requires careful accounting analysis. These paths were not claimed fixed and seller/marketplace features were not disabled. Failed or ambiguous network responses, a process crash after status commit, RLS visibility/configuration differences and concurrent transitions can still leave or hide an inconsistent state. Local unit mocks cannot establish serializable database behavior or actual RLS.
