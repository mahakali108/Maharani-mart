**Status on this branch:** source changes only. Migrations `0070_super_admin_seller_invitations.sql` and `0071_configured_delivery_pins.sql` have been exercised with a local disposable PGlite database, not applied remotely. No PIN coverage or verified public business details have been supplied. No production SQL or Vercel deployment is authorised by this document.

## Deployment prerequisites (requires explicit owner approval)

1. **Identify the target.** Confirm project reference, region, PostgreSQL version, actual migration history and any schema drift using read-only project metadata and queries. One connected project lists migrations through 0069; another has no listed history. Neither was selected as the production target here. Confirm no pending earlier migration, and generate/review a SQL diff. Do not run SQL against an assumed project.
2. **Backup and rehearse recovery.** Owner/DBA confirms an appropriately restorable database backup or PITR checkpoint including `auth.users`, profiles, sellers, invites, policies and orders; record backup timestamp, retention, restore access and restore-time objective. Rehearse restore on an isolated clone and schedule a maintenance window for writes that could be blocked by a new guard. Preserve an app build tag/commit and exact migration hashes.
3. **Review migration effects on a disposable staging clone of the confirmed project.** Apply `0070` then `0071` once in order (after any missing earlier migrations) with the normal migration runner. Confirm role grants, RLS, Auth trigger, staff invite compatibility, seller activation, legacy carts, both atomic order RPCs, concurrent PIN deactivation versus checkout on a real multi-connection Postgres setup, and untouched history. PGlite tests do not prove provider-specific Auth email delivery or real concurrency.
4. **Configure trusted server and Auth settings.** `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` belong to the same target; keep `SUPABASE_SERVICE_ROLE_KEY` server-only (never `NEXT_PUBLIC_`, client bundle, logs or chat). Set `NEXT_PUBLIC_SITE_URL` to the canonical HTTPS origin; configure Supabase Auth Site URL and redirect allow-list for `${NEXT_PUBLIC_SITE_URL}/auth/callback?next=/reset-password`, invite/password setup email delivery, and the sender/template. Verify the complete one-use invitation and password-set flow on staging without storing a plaintext password. Only authorised Super Admins should have `sellers.manage`.
5. **Validate operators and coverage.** Operator confirms each active PIN and its minimum; zero PINs means **all new online self-checkout is blocked**, by design. A positive fee also blocks checkout until split-order fee accounting is designed and tested. Coordinate legacy mobile callers that do not send `addressId`: their new orders fail closed. Do not update existing area assignments by assumption.
6. **Finish publication review.** Obtain verified legal-entity name, postal address, contact/grievance channel, seller-of-record/invoicing model, tax details, retention and privacy disclosures, and approved delivery/returns terms. Revise the draft public pages and obtain qualified Indian legal/tax sign-off before relying on them as policies. Do not publish invented contact or claims.
7. **Only after written approval of the exact target, SQL diff, backup and recovery plan:** schedule migrations **DB first** and verify the production schema; then deploy the same reviewed app commit to Vercel. A new app against old schema errors on missing RPCs; an old app against 0071 correctly has some self-checkout blocked if it lacks structured addresses. Coordinate a short checkout freeze or verified compatible client rollout. Do not automatically run the legacy production-validate script (it performs writes).
8. **Post-deploy smoke and monitoring.** Non-mutating checks: anonymous seller signup denied, Super Admin navigation visible only to authorised actors, static pages load without authentication, unconfigured PIN says unavailable, and PWA assets/manifest/offline page are served. On staging, use dedicated test identities for full invite, order and split-payment scenarios. On production, require separate approval before invitations, PIN activations, test orders or other writes; monitor DB errors, Auth email errors and support reports. Never log invite nonces, addresses or service keys.

## Abort and recovery

If an Auth trigger or RLS regression is observed, suspend seller invitations and new online checkout, preserve forensic evidence, and prepare a reviewed forward migration. Reverting only the app is **not automatically safe** after `0071` because older clients may submit unstructured shipping addresses, and reapplying 0069 over 0070 would remove security guards. Restore from the verified backup under an authorised plan if a forward fix cannot be safely completed. Never use rollback scripts, `DROP ... CASCADE`, force pushes or undocumented live SQL as a quick fix. Historical orders and financial ledger records must survive recovery.

## Remaining verification limits

- Disposable PGlite (Postgres in WASM) is not an actual Supabase project, does not deliver Auth emails, and cannot establish true inter-connection locking behavior. Staging against the identified provider is required.
- Live browser installability, Safari/Android Chrome behavior, screen-reader and 320px/200%-zoom QA need manual device/browser evidence. Static tests are not a substitute.
- No credentials, API keys, personal data or backup files belong in this document or a pull request.
