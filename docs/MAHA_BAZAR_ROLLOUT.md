## Android direct distribution: proposal only

Use the **existing native app**, `com.maharanitraders.app`, minimum API 24 (Android 7). Keep `android/version.properties` as the source for semantic versionName and increasing versionCode. Before a first release, inventory any previously distributed certificates and codes. Use the same release certificate for all upgrades; isolate the signing key in an access-controlled signing environment with encrypted offline recovery and two-person access. No keystore, service key or passwords in the repo or client.

After separate owner approval, add a download page (proposed `/android/download`) and a read-only, revalidated version endpoint (proposed `/api/android/release`). Publish version, code, minimum SDK, release notes, immutable HTTPS artifact URL, size, SHA-256 and certificate fingerprint together, only after release approval. Store binaries outside Git. Verify the artifact hash and signing certificate against the approved release record. Compare version codes, show notes, request explicit consent before download and hand off to Android’s package installer. Explain how to temporarily allow installation from that specific source and revoke it afterwards. Never silently install. PWA icon publication cannot change the native launcher icon: ship a new signed APK.

Require code review, release-device upgrade test, signature verification and owner signoff. For an incident withdraw the download/link and release metadata immediately; do not serve a lower code as an upgrade. Rebuild last-known-good source with a higher code and the same identity. Lost signing identity is a release blocker, not permission to replace the installed app. No Android build or release in this phase.

## Production ordering is a separate owner decision

`lib/compliance/ordering-readiness.ts` requires a verified business profile, configured grievance contacts and a current, unexpired approval for every category in the protected `ordering_launch_readiness` record. These include business identity, public contacts, legal policies, GST/invoicing, marketplace tax/TCS/settlement applicability, delivery/COD/cancellations/refunds, and privacy. Legal/CA applicability and documentary approval must be confirmed by the owner; a passing test or a branding publication is not approval.

Retailer checkout also requires an eligible retailer, an owned structured delivery address, live serviceability for its district/state/PIN, the configured minimum, a resolvable active warehouse, eligible packs, valid server-side prices, quantities and sufficient stock. A positive configured delivery fee currently **blocks online checkout** (`lib/config/delivery-serviceability.ts`); it is not added to the atomic order total. Do not bypass that gate. Verify the invoice issuer and operational delivery/refund arrangements independently before launch. This PR neither reads production readiness values nor activates ordering.
